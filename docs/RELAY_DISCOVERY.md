# Автопоиск транспорта (Relay Discovery)

Статус: **M1–M5 реализованы**: каталог (`internal/discover`), вкладка «Релеи», `qulogicat`, транспорты `storage-webdav` (M3), `cdn-front` (M4), `bot-longpoll` (M5); умный сплит со SNI-sniffing и UDP-дейтаграммы в туннеле (`internal/route`, `internal/vpn`, `internal/tunnel`).

## Проблема

В классической схеме нужен свой сервер за пределами фильтруемой сети:

```text
Классический VPN:   устройство ──► VPS ──────────────────► интернет
                                 (IP пал, SNI виден)

Qulogi сейчас:      устройство ──► VPS ──────────────────► интернет
                                 (камуфляж под vkvideo.ru и т.п.)

Цель автопоиска:    устройство ──► белая платформа ──────► интернет
                    (пакеты живут внутри разрешённого трафика, VPS не нужен)
```

Камуфляж решает проблему «SNI виден», но не решает «IP релея забанен» и «нет своего VPS». Автопоиск закрывает обе: клиент сам находит работающий транзит — будь то релей сообщества, CDN разрешённой платформы или её облачное хранилище.

## Классы транспортов (реестр адаптеров)

| Тип | Схема | Задержка | Нужен VPS | Статус |
|-----|-------|----------|-----------|--------|
| `qulogi-tls` | свой релей `qulogid` с камуфляжем | низкая | да | работает |
| `qulogi-tcp` | свой релей без обёртки | низкая | да | работает |
| `cdn-front` | край белого CDN проксирует на релей за тем же CDN | низкая | да, но IP CDN | работает |
| `storage-webdav` | кадры туннеля как файлы/чанки в белом облаке | секунды | нет | работает |
| `bot-longpoll` | long-poll/bot API белых платформ | секунды | нет | работает |
| `turn-relay` | TURN-серверы (WebRTC-инфраструктура, coturn, cmd/qulogiturn) | низкая | нет | разведка (Allocate) |

Примечания по классам:

- **`cdn-front`** (реализован в M4, `internal/cdnfront`). Клиент соединяется с краем CDN по разрешённому SNI, а внутри HTTP-запросов указывает Host релея, припаркованного за тем же CDN. Туннель едет HTTP/1.1-Upgrade (`Upgrade: qulogi/1` → `101`), дальше — обычный протокол туннеля, включая UDP-дейтаграммы. Клиент: `qulogi -cdn edge:443 -cdn-sni белый.домен -cdn-host relay.example.net`; релей: `qulogid -front :8443` (TLS терминирует CDN; точка входа `/qulogi` маскируется страницей-заглушкой). В каталоге у транспорта поля `addr` (край), `sni` (белый SNI края), `host` (имя релея за CDN) и `ws` (см. ниже).
- **Реальный CDN-фронтинг (M6, WebSocket).** Настоящие CDN-сети проксируют до конца ровно один класс апгрейдов — WebSocket (RFC 6455); произвольный `Upgrade: qulogi/1` и классический кросс-тенантный фронтинг (SNI ≠ Host) крупные сети давят. Поэтому для реальных CDN туннель едет WS-бинарными фреймами: клиент шлёт стандартный WS-хендшейк (`Sec-WebSocket-Key`/`Accept`, `Sec-WebSocket-Protocol: qulogi`), кадры клиент→сервер маскируются по RFC, ping/pong и close обрабатываются кодеком `wsStream`. Постура по умолчанию — same-host камуфляж: SNI = Host = собственный домен релея, припаркованного за CDN (фильтр видит HTTPS к обычному сайту на CDN-сети). Встроенные профили: `cloudflare`, `cloudfront`, `gcore`, `selectel`, `yandex-cloud`, `vk-cloud`. Клиент: `qulogi -cdn edge:443 -cdn-host relay.example.net -cdn-ws` (или `-fallback '{"kind":"cdn",…,"ws":true}'`); релей тот же `qulogid -front` — он принимает и WS, и legacy-апгрейд, старые клиенты совместимы.
- **`storage-webdav`** (реализован в M3, `internal/webdav`). Самый честный путь «устройство → Яндекс → интернет» без VPS: кадры GCM-потока кладутся файлами-чанками (по умолчанию 256 КиБ) в каталог-почтовый ящик `<mailbox>/<session>/up` и забираются из `…/down`. Обе стороны говорят с облаком обычный HTTPS, адрес релея не виден вовсе. Релей следит за базовым каталогом (`PROPFIND`, опрос 2 с) и обслуживает каждую сессию `s-<hex>`; отработанные сессии удаляются. Типичная задержка — 2–4 с (мультисплит-опрос) — годится для веб-сёрфинга, RSS, почты; не для звонков. Клиент: `qulogi -dav https://webdav.yandex.ru -dav-user … -dav-pass … -dav-mailbox qulogi -psk …`; релей: `qulogid -listen "" -dav … -dav-mailbox qulogi -psk …`.
- **`bot-longpoll`** (реализован в M5, `internal/botlp`). Официальные API белых платформ (боты, лонг-поллинг) дают двусторонний канал: кадры едут base64-сообщениями через generic-контракт `POST {base}/send` / `GET {base}/poll?seq&wait` (FIFO на комнату); сессии объявляются в контрольной комнате `<base>-ctl`, кадры сессии — в своей комнате, ответы — в `<room>-r`. Платформенный мост (VK/Max/свой glue) — тонкий шим над контрактом; обе стороны говорят только с платформой, адрес релея нигде не виден. Клиент: `qulogi -botlp https://api.example/bot -botlp-token … -botlp-room owl`; релей: `qulogid -botlp … -botlp-room owl`. Задержка — секунды, годится как запасной транспорт.
- **`turn-relay`.** WebRTC-релеи белых сервисов иногда доступны как открытые релеи; при обнаружении это идеал: низкая задержка и полностью разрешённый адрес. Требует регулярного сканирования.

## Каталог релеев (формат v1)

Каталог — подписанный JSON. Публикуется на нескольких зеркалах: обычный HTTPS, DNS TXT (фрагментами), белые облачные хранилища, QR/ссылки-инвайты. Клиент пытается все зеркала параллельно и берёт первое, чья подпись сходится с пиновым ключом. Последний хороший каталог кэшируется локально и выручает, когда все зеркала недоступны.

### Зеркала

| Тип | Как выглядит | Заметки |
|-----|--------------|---------|
| `https` | `{"type":"https","url":"https://…/catalog.json"}` | GitHub raw, jsDelivr, любые статические хостинги |
| `dns-txt` | `{"type":"dns-txt","name":"_qulogi.example.org","server":"77.88.8.8:53"}` | собственный DNS-клиент поверх UDP — работает без системного резолвера; HTTPS по указателю из TXT, если запись не влезает |
| `doh` | `{"type":"doh","name":"_qulogi.example.org","url":"https://dns.google/dns-query"}` | RFC 8484, wire-format POST |

Официальный community-каталог живёт в [mel0k1/qulogi-catalog](https://github.com/mel0k1/qulogi-catalog): оба HTTPS-зеркала из таблицы указывают на него, PR с релеями подписываются сопровождающими, CI репозитория проверяет подпись на каждый PR. Публичный ключ (`discover.CommunityPubKeyB64`) зашит в клиентов: каталог без верной подписи отвергается — compromised-зеркало может подсунуть только более старый, всё ещё подписанный список.

TXT-_payload: либо одна строка `https://…` — указатель на HTTPS-каталог, либо base64 каталога, нарезанный на строки по 200 символов с двузначным шестнадцатеричным префиксом порядка (`00…`, `01…`). Клиент собирает строки, сортирует по префиксу и декодирует.

```json
{
  "version": 1,
  "updated": "2026-10-26T12:00:00Z",
  "ttl_min": 120,
  "key_id": "qulogi-dir-2026q4",
  "relays": [
    {
      "id": "owl-eu-1",
      "region": "eu-central",
      "weight": 60,
      "transports": [
        { "type": "qulogi-tls", "addr": "r1.example.net:443", "sni": "vkvideo.ru", "fp": "b3x9…" },
        { "type": "cdn-front",  "addr": "https://r1.example.net/edge", "sni": "cdn.whitelisted.ru" }
      ]
    }
  ],
  "sig": "…base64 Ed25519…"
}
```

Подпись накрывает канонический JSON без поля `sig` (реализация: `discover.Directory.Sign/Verify`). Свежесть ограничивается `ttl_min` — устаревший каталог отбрасывается даже с верной подписью.

## Пайплайн клиента

1. **Bootstrap.** Хоть одно зеркало каталога должно быть достижимо: список зеркал зашит в сборку + кэш последнего рабочего зеркала локально.
2. **Верификация.** Ed25519 по пиновому ключу, TTL, структурная валидация.
3. **Пробник.** Параллельная разведка каждого транспорта (16 горутин, общий бюджет): TCP-dial как база, для `turn-relay` — полноценный STUN Allocate (это единственный честный сигнал живости TURN-сервера).
4. **Выбор.** Сортировка по `RTT × (1 − weight/200)` — операторская подсказка дисциплинирует, но не перекрывает факты.
5. **Подключение** к лучшему, остальные — в тёплый резерв.
6. **Health-check** раз в N секунд; деградация → автоматический переезд на следующий кандидат без участия пользователя.

Всё это уже работает на уровне каталога: `discover.Pick(ctx, dir, n, budget, probe)`.

### turn-relay (реализован)

Клиент `internal/turnrelay` говорит стандартный STUN/TURN (RFC 5766) поверх TCP-транспорта и открывает TCP-связку с релеем через RFC 6062: Allocate (с long-term-креденшелами или анонимно) → Connect → ConnectionBind — дальше это обычный поток, по которому едет штатный туннель. TURN-серверы существуют ради WebRTC, поэтому они доступны из большинства фильтрующих сетей; в проводе видны только STUN и опакеченный туннель.

- **Разведка** — `turnrelay.Probe`: честный Allocate с замером RTT; автопоиск вызывает её для транспортов класса `turn-relay` вместо TCP-dial (каталог: `addr` = TURN-сервер, `host` = адрес релея за TURN).
- **Самохостинг** — `cmd/qulogiturn` (минимальный RFC 6062-сервер для сообщества и smoke-тестов); продакшен-деплой — coturn с включённым TCP-relay.
- **Креденшелы** — опционально: без user/pass работает анонимно; с ними — long-term (MD5 user:realm:pass), nonce/realm подхватываются из 401-челленджа.

### Мосты botlp под конкретные платформы (реализованы)

Мосты (`internal/botlp`: `chat.go`, `vk.go`, `max.go`) мапят Bot API реальных платформ на generic send/poll контракт. Кадры едут текстами сообщений одного чата с тегом `qulogi|<комната>|<base64>`; каждая сторона держит свой курсор глобального потока, направление различается комнатами (клиент пишет <room>, читает <room>-r, релей наоборот — никто не читает свои кадры).

- **vk** — `messages.send` + `groups.getLongPollServer` (a_check, wait 25с); ограничение VK 4096 символов на сообщение → чанк кадра 2800 байт.
- **max** — `botapi.max.ru`: POST /messages + GET /updates (marker long-poll, TamTam-совместимый формат).
- **Требование платформ**: бот не видит свои сообщения, поэтому обе стороны транспорта держат РАЗНЫЕ токены ботов в одном чате (peer_id/chat_id общий) и включают приём сообщений от ботов. Токен каждого бота — секрет его стороны.
- Выбор адаптера: `botlp_kind` (`generic`|`vk`|`max`) + `botlp_chat` в конфиге, флаги `-botlp-kind/-botlp-chat` в CLI.

## Авто-переезд на резервный транспорт

Деградация активного транспорта — норма (CDN начал резать WS, облако затормозило, платформа ужесточила лонг-полл), поэтому движок держит цепочку транспортов: основной — из плоских полей конфига, резервы — `fallbacks` (JSON-спеки `TransportSpec`: `kind` `tcp|cdn|turn|dav|botlp` + адреса/креденшелы).

- **Диал-путь.** Каждое новое соединение пытается активный транспорт, при ошибке — резервы по порядку (охлаждённые — в конце, бюджет 25с). Успешный резерв становится «липким» активным, счётчик переездов виден в статусе и в приложении.
- **Монитор.** Раз в 15с (`-probe-secs`) проба активного транспорта сквозным хендшейком туннеля (цель — TEST-NET, релей её чисто отвергает); две подряд неудачи — охлаждение на 30с и переезд на живой резерв. Дорогие резервы (botlp/dav) проактивно не пробуются — только при переезде.
- **Возврат.** Когда активен не лучший кандидат, монитор пробует старшие; восстановился — цепочка возвращается наверх, в логе `failover: … -> …`.
- **Проводка.** CLI: `-fallback` (повторяемый), `-no-failover`, `-probe-secs`. Приложение: секция «Авто-переезд при деградации» (JSON-массив резервов + выключатель), автоподключение само выстраивает резервы из остальных живых транспортов каталога; на главном экране — активный транспорт и число переездов.

## Автоподключение одним тапом (UX-обвязка)

Кнопка «Автоподключение» на главном экране закрывает весь пайплайн без ручных настроек: гонка зеркал → верификация → разведка (для turn-relay — реальный Allocate) → лучший кандидат по RTT×вес → раскладка в конфиг (очистка конкурирующих транспортов) → старт движка (VPN или SOCKS-режим). Результат показывает чипом: `лучший: <релей> · <тип> · <RTT> мс`. Ручные пути (инвайты, QR, вкладка «Релеи») никуда не делись — автоподключение лишь надстройка над ними.

## Приватные релеи и инвайты

Публичный каталог — для сообщества; личные релеи распространяются ссылками вида:

```text
qulogi://relay/owl-eu-1?type=qulogi-tls&addr=r1.example.net%3A443&sni=vkvideo.ru&psk=…
qulogi://catalog/?url=https%3A%2F%2Fmirror.example%2Fcatalog.json&name=Community
```

`psk` в ссылке обязателен для qulogi-транспортов (клиент должен аутентифицироваться на qulogid), поэтому инвайт — это секрет: распространяйте его как пароль. В приложении ссылка импортируется тремя путями: вставить текст, отсканировать QR, открыть deep link `qulogi://` — Android ловит схему и передаёт её в приложение. Любой релей можно отправить обратно QR-кодом с вкладки «Релеи».

Каталоги подписываются утилитой оператора `qulogicat` (`-gen` → ключи, `-in relays.json -out catalog.json` → подписанный каталог, `-txt` → строки для DNS-зоны):

```bash
qulogicat -gen
qulogicat -key <seed> -in relays.json -out catalog.json -ttl 120 -key-id qulogi-dir-2026q4
qulogicat -key <seed> -in relays.json -txt        # куски base64 для TXT
qulogicat -txt -url https://mirror.example/catalog.json   # или указатель
```

## Умный сплит (реализован, важно для мобильных)

В whitelist-режиме туннелировать всё — расточительно и палевно. Клиент держит локальную таблицу маршрутов (`internal/route`):

- разрешённый трафик пускает напрямую (быстро, без нагрузки на релей);
- остальное — через туннель или best-транспорт из каталога;
- правило «всегда через релей» перекрывает белый список; пользовательские правила перекрывают встроенные.

Встроенный стартовый список — Яндекс, VK/Mail.ru, банки, госсервисы, маркетплейсы, крупные операторы плюс основные сети этих платформ. В SOCKS-режиме сплит работает по домену назначения. В VPN-режиме TUN-стек подглядывает SNI: первые байты каждого TCP-потока буферизуются (`internal/vpn/sniff`), из ClientHello извлекается hostname (`transport.ParseClientHello`), и решение direct/tunnel принимается уже по домену; не-TLS и «молчаливые» потоки (SSH, SMTP) не страдают — окно подглядывания 1 с, дальше поток идёт по IP-политике. DNS в split-режиме ходит по TCP внутри туннеля (защита от подмены ответов), а прочий UDP с 0.4 ездит по туннелю фреймированными дейтаграммами: QUIC и игры работают через релей, белый UDP по-прежнему идёт напрямую.

Это экономит батарею и трафик релея и делает образ трафика естественнее: типичные для пользователя белые сервисы ходят как ходили.

## Риски и границы

- **ToS платформ.** Storage/bot-транспорты используют API не по назначению: возможны блокировки аккаунтов-ретрансляторов. Релеи должны быть одноразовыми и взаимозаменяемыми.
- **Задержки.** Storage-класс — секунды; подходит не под все задачи, приложение должно честно показывать класс транспорта.
- **Хрупкость cdn-front.** CDN может начать сверять SNI/Host в любой момент — поэтому транспортов в каталоге несколько, и выбор автоматический.
- **Юридическое.** Проект для восстановления доступа к информации; использование API сторонних сервисов — на страх и ответственность оператора релея.

- [x] **UDP в туннеле** — фреймированные дейтаграммы (старший бит ATYP в заголовке адреса), QUIC и прочий UDP едут через релей; v0.3-серверы отвергают такие сессии чисто, TCP-совместимость полная в обе стороны
- [x] **M6** — доменный фронтинг через реальные CDN: WS-кодек RFC 6455 (`cdnfront.WSFront`/`wsStream`), профили реальных CDN, флаг `ws` в каталоге, совместимость с legacy-апгрейдом
- [x] **Авто-переезд** — цепочка транспортов в движке (`fallbacks`), монитор деградации с пробой сквозным хендшейком, липкий активный транспорт, возврат на лучший; резервы из автоподключения
- [x] **Сплит** — умный сплит по белым спискам (`internal/route`), встроенный список + пользовательские правила, пер-поточная маршрутизация в VPN и SOCKS-режимах
